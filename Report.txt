# Звіт з лабораторної роботи: CI/CD для мікросерсісного проєкту

## Мета роботи
Підключити CI/CD-конвеєр до мікросерсісного проєкту з лабораторної роботи №1 (FastAPI-сервіси `core_service` та `analytics_service` з Docker-образами) та налаштувати захист основної гілки.

## Обраний інструмент
**GitHub Actions** — нативний CI/CD-сервіс GitHub, оскільки проєкт розміщений у репозиторії `Markovoloshchuk/DevOps-Project`. Увесь конфігураційний файл пайплайну знаходиться у **`.github/workflows/ci.yml`**.

## Що було зроблено

**1. Підключення CI/CD.** Налаштовано автоматичний запуск пайплайну при кожному `push` у гілку `main` та при кожному Pull Request. Статуси виконання відображаються безпосередньо в інтерфейсі PR.

**2. Збірка та тестування сервісів.** Для кожного сервісу створено окремі завдання (job'и) через **матрицю** (`core_service`, `analytics_service`), які виконуються паралельно та незалежно (`fail-fast: false` — падіння одного не скасовує інші). Кожен job містить кроки Build (`python -m compileall` — компіляція) та Test (`pytest`). Залежності кешуються через `actions/setup-python` з `cache: pip` для прискорення повторних запусків.

**3. Статичний аналіз коду.** Підключено лінтер **Ruff** окремим блокуючим job'ом `Lint (Ruff)`. Конфігурація у файлі `ruff.toml` містить обґрунтовані локальні винятки (наприклад, правило B008 для ідіоматичного патерну FastAPI `Depends(...)`). Виявлені порушення були виправлені; результат перевірки доступний у вигляді статусу в PR.

**4. Збірка контейнерних образів.** Job `Build image (...)` залежить від успішного завершення усіх перевірок через `needs: [lint, test]`. Образи збираються окремо для кожного сервісу з використанням Dockerfile із лабораторної роботи №1, **лише локально в ренері** (`push: false`), з кешуванням шарів Docker (`cache-from/to: type=gha`). Додано рекомендоване блокуюче сканування зібраного образу на вразливості інструментом **Trivy** (рівні CRITICAL/HIGH) перед публікацією.

**5. Публікація образів у реєстрі.** Образи публікуються у **GitHub Container Registry (ghcr.io)** лише при `push` у основну гілку (умова `if`), ніколи — при PR. Автентифікація виконується через вбудований токен `GITHUB_TOKEN` (облікові дані в CI-секретах, у репозиторії не зберігаються). Кожен образ отримує два теги: унікальний **`sha-<коміт>`** та **`latest`**. Працездатність підтверджено: `docker pull ghcr.io/markovoloshchuk/core_service:latest` + запуск обох сервісів у спільній мережі; відповіді `curl` підтвердили `{"status":"ok"}` та `"core_service_status": "ok"`.

**6. Захист основної гілки.** Увімкнено Branch Protection Rules для `main`: заборона прямого push (обов'язковий PR) та **required status checks** — `Lint (Ruff)`, `Test (...)`, `Build image (...)`. Демонстровано неможливість злиття: створено гілку `demo/broken-test` із навмисно зламаним тестом → у PR статус `Test (core_service)` ❌, кнопка Merge заблокована з повідомленням *«Merging is blocked — Required status checks must pass»*.

## Результат
Побудовано повноцінний CI/CD-конвеєр: **CI** (лінтинг → тести → збірка → сканування безпеки) та **CD** (автоматична публікація образів у реєстр). Зламаний код фізично неможливо злити в `main`. Усі 6 пунктів лабораторної роботи виконано; усі job'и пайплайну проходять успішно.

---

*Прикріпити скріншоти: (1) зелений прогін CI/CD з усіма job'ами; (2) відповіді `curl` до запущених із реєстру образів; (3) сторінка Packages із опублікованими образами; (4) заблокований PR із червоним статусом тесту.*

---

Якщо треба — можу скоротити до півтори сторінки, розширити з кодом конфігу або переформатувати під конкретний шаблон звіту твого викладача.
